图 0 · 题目：输入和输出

人话：同一个人的领英主页被抓了很多次，每次抓到的工作经历都不全、还可能改过字。要做的是：每个人、每个抓取日期，给出当天已知的最完整履历，每段工作一个永远不变的 id，而且不能用未来的信息。

输入（同一个人 user 7 的三次抓取）
asof        company      title               start
2024-01-05  Google       Software Engineer   2022-03
2024-03-10  Google       Senior SWE          2022-03      ← 改了头衔（Case B）
2024-06-02  Meta         ML Engineer         2024-05      ← 这次没抓到 Google（Case A）

输出
asof        position_id   company   title             start
2024-01-05  7·2^16+0      Google    Software Engineer  2022-03
2024-03-10  7·2^16+0      Google    Senior SWE         2022-03   ← 同一个 id，用最新值
2024-06-02  7·2^16+0      Google    Senior SWE         2022-03   ← 没抓到也照样带着
2024-06-02  7·2^16+1      Meta      ML Engineer        2024-05

Case A: a scrape misses a position, so we carry known positions forward. Case B: the same position comes back edited, so we match it and keep the latest non-null value per field.

Case A = 漏抓了照样带着；Case B = 改了字要认出是同一段并用最新值。

讲这张图时说什么

People are independent, so I hash users into 64 buckets and process buckets in parallel. Each bucket is cleaned, then every person is replayed snapshot by snapshot in date order. The state at the end can be saved and continued the next day.

人和人互不相关 → 按 user_id 分 64 桶并行；桶里先清洗，再每人按日期逐个快照处理；最后的状态能存下来，第二天接着跑。

讲这张图时说什么

The step function only sees the current snapshot and the state built from earlier ones. So it can't use future information by construction, not by discipline. A test plants a future snapshot and checks it never shows up earlier.

step 只能看见「这一次的快照 + 之前攒下的状态」，结构上就不可能偷看未来；还有测试专门塞一个未来快照验证。

step.py
def step(state, observed_ts, rows):
    fp = fingerprint(rows)                 # 和上一次一模一样？
    if fp != state.last_fingerprint:       # 57.5% 的快照是重复的，直接跳过
        rows = dedupe(rows)                # 规则 1
        assigned = match(rows, state.positions)   # 规则 2–5
        for i, row in enumerate(rows):
            pos = assigned[i] if i in assigned else state.new_position()
            pos.absorb(row)                # 最新非空值覆盖
        state.merges += consolidate(...)   # 规则 6：折叠重复 id
    return [当天每一段已知职位]              # Case A：没抓到的也输出

状态里存什么（state.py）：每段职位的字段值 + 别名集合（用过的所有公司名、URL、头衔）；next_seq；上一次的指纹和日期。

id 怎么来：user_id × 2^16 + 序号。不用全局计数器，同样输入永远得到同样 id；id 只会退休（被折叠）不会改变。

数据告诉我什么 → 所以这么设计（README 第 2 节）

先看数据再定规则。每一条都是「数据里看到的现象 → 对应的设计决定」，这是整份作业最能体现思考的部分。

数据里看到的所以这么设计
52% 的快照只有一行；30% 的人从来不超过一行Case A（沿用已知职位）是常态，不是特例：一次抓取只抓到最上面一段，不代表别的工作没了，所以已知职位一直带着往后输出
57.5% 的快照和上一次一模一样用指纹直接跳过，省掉一半最贵的匹配
7.9 万组「同雇主同开始但头衔不同」：一半是同一份写两遍，一半是真的并行职位不能只看雇主 + 开始日期，还要比头衔
约 20% 的开始日期是 1 月 1 日当成「只写了年份」（见下面）
有的抓取所有头衔都是空的（降级抓取）空头衔当通配，但只在这一行内有效，不存成别名（存了就会吞掉以后所有头衔，Veeva 那个 bug）
URL 列在样例里叫 company_website两个名字都收，输出一律叫 company_linkedin_url
乱码（ä¸€æ±½-å¤§ä¼— = 一汽-大众）和丢了反斜杠（Lloydu2019s = Lloyd's）清洗时无损修复：cp1252 回转 + 转义解码，修了 16,314 个格子
坏数据不到 0.1% 的行只丢坏的那一行；整次快照只有每行都坏才丢（390 万次里 2,539 次）

「只写了年份」具体怎么处理（match.py start_compatible）：很多人只填年份，系统存成那年的 1 月 1 日。所以比较两个开始日期时，如果同一年、并且有一边是 1 月 1 日，就当成兼容。例：一次写 2020-01-01（只填了年），一次写 2020-06-01（填了月份）→ 相差 5 个月，超过平时允许的 62 天，但因为是同一年且一边是 1 月 1 日，仍然算同一段的候选。只用在规则 2 找候选这一步。

About 20% of start dates are January 1, which usually means only the year was entered. So two starts in the same year count as compatible when either one is January 1, even though they're more than two months apart.

你的决定（顺口带出来）：

  • 只丢坏行，不丢整次快照：你当时说「整次丢掉很可惜」。
  • 输入文件是按行切的，不是按人切的：同一个人的不同次抓取散在好几个文件里，所以一定要先按 user_id 分桶，才能把一个人的所有数据凑到一起。

Every rule came from the data: half the snapshots have one row, so carrying positions forward is the normal case; 57.5% repeat, so a fingerprint skips them; titles can be all null in degraded scrapes, so a missing title is a wildcard only for that row; and fewer than 0.1% of rows are bad, so I drop rows, not whole snapshots.

技术选型：为什么这么选（1 分钟）

选项好处问题结论
pandas人人会基本单核；字符串存成 Python 对象，2.5 GB 数据进内存会膨胀到十几 GB，4 核 16 GB 会爆不选
DuckDBSQL 好读、超内存自动落盘、很快核心是「每人按时间一步步推进的状态机 + 模糊配对」，写成 SQL 很别扭，最后还得调 Python，两个引擎来回切不选（纯 SQL 题会选它）
PySpark 本地模式和生产同一套代码JVM 启动慢、镜像 1 GB+，单机 1000 万行反而比 Polars 慢，而且评分要计时交作业不选，生产选
PolarsRust 多线程、惰性执行只读需要的列、Python 写法干净；和 Arrow 零拷贝，能直接交给 Spark超内存落盘不如 DuckDB；版本间 API 变化快选：落盘问题用「自己先按人分桶」解决，版本锁死
  • rapidfuzz：C++ 写的字符串相似度库，token_set_ratio 就是它的，比纯 Python 快很多。
  • uv：锁定所有依赖的精确版本（uv.lock），镜像每次构建都一样。
  • Docker：基础镜像按摘要钉死、非 root 用户运行、输入只读挂载、可以 --network none 断网跑、不放任何密钥。
  • polars-lts-cpu：普通版 Polars 需要 AVX2 指令，在 Mac 上模拟 x86 的 Docker 里会卡死；lts-cpu 版不依赖 AVX2。
  • 混合写法：能向量化的（读、清洗、分桶、排序）交给 Polars；只有逐人的状态机和模糊配对走 Python + rapidfuzz。

I chose Polars over pandas because pandas is mostly single-threaded and would blow up memory, and over DuckDB because the core is a per-person state machine with fuzzy matching, which is awkward in SQL. Spark is the production answer, but locally it's slower and the image is huge. Polars hands Arrow tables to Spark with zero copy, so the same function runs in both.

Matching is greedy by score: title similarity from 0 to 100, plus 25 for the same employer, 10 for the same start and 5 for the same end. Below 55 the row opens a new position.

打分 = 头衔相似度 + 同雇主 25 + 同起始 10 + 同结束 5；低于 55 开新职位。

逐个名词

  • 线性扩展：人和人之间没有任何共享的东西，每个人单独算。所以数据翻一倍，总工作量就翻一倍；机器翻一倍，时间就减半。不会因为数据变大，出现「每个人都要和其他所有人比」这种越来越慢的情况。
  • 约 800 核时：实测单机 4 个进程，1150 万行约 78 秒 → 每个 CPU 核每秒约处理 3.5 万行。1000 亿 ÷ 3.5 万 ≈ 286 万核秒 ≈ 800 核时（一个核要干 800 小时）。分给 64 个核同时干 ≈ 12.5 小时；给 640 个核 ≈ 1.25 小时。
  • Spark 适配器 70 行：spark/coalesce_spark.py 只有约 70 行，只负责「外层」：读数据、按 user_id 分区、把每个分区交给 coalesce_bucket、把结果写回去。匹配规则、id、状态一行都没写在这里。
  • 跑同一个函数：单机版和 Spark 版调用的是同一个 coalesce_bucket，规则只有一份，改一处两边都生效，不会出现两套逻辑结果不一样。
  • mapInArrow：Spark 的一个接口，把每个分区的数据以 Arrow 表的形式交给一个 Python 函数，函数返回 Arrow 表。Arrow 是列式内存格式，Spark 和 Polars 都认，所以在两者之间传数据几乎不用拷贝转换。
  • 在 2 个文件上逐行一致：拿 2 个输入文件，单机版跑一遍、Spark（本机模式）跑一遍，把两份输出逐行比，每一行都一模一样（73 万多行）。证明 Spark 外壳没有改变结果。

要主动说的局限（面试官问到就照实说）：

  • 没在真集群上跑过，只在本机 Spark 上验证过。800 核时是按单机速度推算的。
  • Spark 版目前只做一次性全量：增量状态和隔离没接进去，代码注释里写了接法（当天数据按 user_id 和状态表 join，每个分区调 coalesce_bucket(df, states)，再 MERGE 回状态表）。
    The Spark version only does a one-off full run so far; incremental state and quarantine aren't wired in yet. The plan is to join each day's data with the state table on user_id, call coalesce_bucket(df, states) per partition, and MERGE the new state back.
  • 每个分区是整个读进内存的。1000 亿行 ÷ 4096 个分区 ≈ 每个分区 2,400 万行，会太大；真跑要把分区数调到每个分区几十万行（几十万个分区），和单机版每桶约 18 万行同一个量级。
  • 生产里状态应该放按 user_id 分区、只追加的表（比如 Iceberg / Delta），而不是现在的 parquet 文件。为什么：
    1. 现在每天整份重抄：--state-in 读昨天的文件夹，--state-out 写一个全新的文件夹，64 个桶每个都整份重写，哪怕今天只有 1% 的人有新数据。用表就可以只更新（MERGE）今天动过的那些人。比方：现在是每天把整本账抄一遍，表是只改动过的那几页。
    2. 按 user_id 分区 = 只读需要的：今天只有某些人有新数据，按 user_id 分区后只读这些人所在的分区（分区裁剪），不用把全部状态读进来；和当天数据 join 时也天然对齐。
    3. 整次提交要么全成功要么全不算：现在是每个文件单独原子写，64 个文件之间没有整体保证，跑到一半挂了会新旧混在一起（现在靠写到新文件夹规避）。Iceberg / Delta 有事务：一次运行整体提交，读的人永远看到完整的一版。
    4. 旧版本都留着（时间旅行）：只追加 = 不覆盖旧数据，每次提交是一个新版本。某天跑坏了可以直接回退到昨天的状态；也能查「某一天我们知道的是什么」，正好对上 as-of 的需求和审计。
    5. 其他：加字段不用重写全表（schema 演进）；小文件自动合并；多个任务同时读写不会读到一半的数据。
    Today each run rewrites every bucket's state into a new folder, even if only 1% of people changed. A table partitioned by user_id lets a run MERGE only the touched users and read only their partitions. Iceberg or Delta also gives one atomic commit per run instead of 64 separate files, and keeps old versions, so a bad run can be rolled back and we can ask what we knew on any date, which fits the as-of model.

People are independent, so the work grows linearly. Measured at about 35 thousand rows per core-second, 100 billion rows is roughly 800 core-hours, about 12 hours on 64 cores. The Spark adapter is about 70 lines: it repartitions by user_id and calls the same coalesce_bucket through mapInArrow, so there's one copy of the logic. On two input files it matched the single-machine output row for row. I haven't run it on a real cluster, incremental state isn't wired into it yet, and at that scale I'd raise the partition count so each partition stays around a few hundred thousand rows.

一句话：判官只是离线的考官，用来给规则打分、找错，不在流水线里，也没用来训练或微调任何模型。

  • 打分：每一类决定（合并了头衔大改 / 中改、同雇主开新 id、同雇主同开始却分开）抽 75 个，问「一份还是两份」，算出每类的准确率。

The judges are offline graders, not part of the pipeline and not used for training.   • 半天 + 增量 = 全量（test_full_run_equals_half_plus_incremental）：把样例数据按日期从中间切成前后两半。先只跑前一半、存下状态；再读这个状态跑后一半。把两次的输出拼起来，和一次性跑全部数据比，必须完全一样。它同时证明了两件事：增量没算错；前一半跑的时候根本看不到后一半，结果却一样，说明全量跑时也没用到未来信息。

「改成别名集合」是什么意思：每个职位不只记一个公司名、一个头衔，而是把出现过的所有公司名、URL、头衔都存进一个集合（company_keys、url_keys、title_keys）。以后新来一行，只要和集合里任何一个对上就能认出来。输出时仍然显示最新的那个值。一句话：认人用全部历史，展示用最新值。Febase 改回原名时，原名还在集合里，所以能认回同一个 id。

「日期乱跳」是什么：一个 id 的开始日期一会儿是 2019 一会儿是 2022，因为两段不同时期的同名工作被并成了一个 id，absorb 每次用最新的值覆盖。再入职单独开 id 之后，这种情况变成 0。

主要取舍：merge when in doubt。漏合并 = 一个重复的 id 永远带下去；错合并 = 丢一个头衔。前者更常见、更伤。

Storing only the latest value broke when someone renamed their employer and later renamed it back, so each position keeps alias sets for names, URLs and titles: match on any alias, display the latest. ASCII-only normalisation turned 228k non-Latin titles into empty strings that matched anything, so I switched to Unicode. Treating a rehire as a new position added 1,579 ids, removed all 939 ids whose dates jumped around, and was right 57 of 58 times.

To sum up · 总结

  • 核心：每个人一个状态机，按日期一次喂一个快照，所以从结构上就不可能用到未来信息。
  • 匹配：六条规则 + 打分（头衔相似度 + 同雇主 25 + 同开始 10 + 同结束 5，≥ 55 才配），取舍是 merge when in doubt。
  • 规模：人和人独立 → 按 user_id 分桶并行，线性扩展；单机 1150 万行 75–78 秒，1000 亿行约 800 核时；Spark 跑同一个函数。
  • 每天更新：存状态接着跑，只动有新数据的人；迟到数据只重放那一个人。
  • 评估：没有标准答案 → 分层抽样 + 两个 LLM 判官 + 60 对人工 + 不用评委的检查；每个发现都变成一条规则和一个回归测试。

为什么不直接让 LLM 判每一对（面试官很可能问）

  • 规模：1000 亿行，每对都调一次 LLM，成本和时间都不现实；规则版只要约 800 核时。
  • 可复现：id 必须稳定，同样的输入每次都要给同样的结果；LLM 的回答会变。
  • 可解释：规则每一步都说得清为什么，出错能定位到是哪条规则。
  • LLM 放在哪：放在离线评估里当考官，抽样打分、找错，不放在每一行都要走的路径上。

Why not have an LLM judge every pair? At 100 billion rows it's far too slow and expensive, and ids must be reproducible, which an LLM's answers aren't. Rules are explainable and each error points to one rule. So the LLM sits offline as a grader on samples, not on the hot path.

conform　src/coalesce/schema.py 第 50–70 行

把任何一份输入整理成标准样子，四步：① 只有 company_website 时改名成 company_linkedin_url；② 对照 10 列，缺哪列就直接报错（SchemaError），不带着错数据往下跑；③ 逐列转类型：日期先按「微秒时间戳」读再截成日期，所以给日期、时间戳都能接；strict=False 表示转不了的值变成空值，交给后面清洗去丢；④ 文本只留前 4000 字符，防止个别巨长的行撑爆内存。整个过程是 LazyFrame（惰性执行），真正读文件时才执行，而且只读需要的列。Spark 版本调用的也是它，所以两边输出一模一样。

def conform(lf: pl.LazyFrame) -> pl.LazyFrame:
    """Rename, type-coerce and truncate an input frame to ``INPUT_SCHEMA``."""
    cols = set(lf.collect_schema().names())
    if URL_IN in cols and URL_OUT not in cols:
        lf = lf.rename({URL_IN: URL_OUT})
        cols = (cols - {URL_IN}) | {URL_OUT}
    missing = set(INPUT_SCHEMA) - cols
    if missing:
        raise SchemaError(f"input is missing columns: {sorted(missing)}")
    casts = []
    for name, dtype in INPUT_SCHEMA.items():
        expr = pl.col(name)
        if dtype == pl.Date:
            # Accept datetimes/timestamps too; the assignment only needs day precision.
            expr = expr.cast(pl.Datetime("us"), strict=False).cast(pl.Date)
        else:
            expr = expr.cast(dtype, strict=False)
        if dtype == pl.String:
            expr = expr.str.slice(0, MAX_TEXT_LEN)
        casts.append(expr.alias(name))
    return lf.select(casts)

bucket_expr　src/coalesce/partition.py 第 15–18 行

算每一行属于哪个桶：abs(user_id) % n_buckets。同一个人永远进同一个桶。用自己写的取模而不是 Polars 自带的 hash，因为后者换版本会变，而状态文件是按桶存的，第二天同一个人必须回到同一个桶。

def bucket_expr(n_buckets: int) -> pl.Expr:
    """``user_id % n``: a hash we own, so a user lands in the same bucket (and finds the
    same state file) across Polars versions. ``Expr.hash`` is not stable across versions."""
    return (pl.col("user_id").abs() % n_buckets).cast(pl.Int32).alias("bucket")

partition_input　src/coalesce/partition.py 第 21–33 行

把输入切成 64 个桶：先建好 64 个文件夹 bucket=0 … bucket=63；然后一次只读一个输入文件，按桶号拆开，每一份写成一个小 parquet，写完立刻释放内存（del df）。所以不管输入多大，这一步的内存上限都只是「一个输入文件」。

def partition_input(input_dir: Path, work_dir: Path, n_buckets: int) -> list[Path]:
    """Write ``work_dir/bucket=<k>/part-<i>.parquet``; return the bucket directories."""
    files = sorted(input_dir.glob("*.parquet"))
    if not files:
        raise FileNotFoundError(f"no parquet files in {input_dir}")
    for k in range(n_buckets):
        (work_dir / f"bucket={k}").mkdir(parents=True, exist_ok=True)
    for i, f in enumerate(files):
        df = conform(pl.scan_parquet(f)).with_columns(bucket_expr(n_buckets)).collect()
        for (k,), part in df.partition_by("bucket", as_dict=True).items():
            part.drop("bucket").write_parquet(work_dir / f"bucket={k}" / f"part-{i:04d}.parquet")
        del df  # keep the parent's footprint to one input file at a time
    return [work_dir / f"bucket={k}" for k in range(n_buckets)]

def run(input_dir: Path, output_dir: Path, *, n_buckets: int = 64, workers: int | None = None,
        state_in: Path | None = None, state_out: Path | None = None,
        work_dir: Path | None = None, report_dir: Path | None = None) -> dict:
    """Partition the input by user, coalesce the buckets in parallel, write outputs atomically.

    ``output_dir`` receives only the output parquet files, so any reader can treat it as
    one dataset. Metrics and quarantined users go to ``report_dir`` when given.
    Returns the run metrics.
    """
    t0 = time.perf_counter()
    output_dir.mkdir(parents=True, exist_ok=True)
    if work_dir is not None:
        work_dir.mkdir(parents=True, exist_ok=True)
    if state_in is not None:
        _check_state_layout(state_in, n_buckets)
    tmp_root = Path(tempfile.mkdtemp(prefix="coalesce-", dir=work_dir))
    saved_threads = os.environ.get("POLARS_MAX_THREADS")
    try:
        buckets = partition_input(input_dir, tmp_root, n_buckets)
        t_part = time.perf_counter() - t0
        jobs = [BucketJob(k, b, output_dir, state_in, state_out, report_dir) for k, b in enumerate(buckets)]
        # One Polars thread per worker: the per-user loop is Python-bound, and N workers
        # each spawning a full thread pool oversubscribes the CPUs (measured 2.7x slower).
        # Spawned children read the env at import, so set it before creating the pool.
        os.environ["POLARS_MAX_THREADS"] = "1"
        workers = workers or available_cpus()
        with ProcessPoolExecutor(max_workers=workers,
                                 mp_context=multiprocessing.get_context("spawn")) as ex:
            per_bucket = list(ex.map(process_bucket, jobs))
    finally:
        shutil.rmtree(tmp_root, ignore_errors=True)
        if saved_threads is None:
            os.environ.pop("POLARS_MAX_THREADS", None)
        else:
            os.environ["POLARS_MAX_THREADS"] = saved_threads
    if state_out is not None:
        (state_out / "_meta.json").write_text(json.dumps({"n_buckets": n_buckets}))

def fingerprint(rows: list[dict]) -> int:
    """Stable across processes (unlike ``hash``), so it can live in saved state."""
    # repr per row so None/str/date mix sorts without TypeError; order-insensitive.
    canon = "\n".join(sorted(repr(tuple(r[f] for f in FIELDS)) for r in rows))
    return int.from_bytes(hashlib.blake2b(canon.encode(), digest_size=8).digest(), "big")

def step(state: UserState, observed_ts: dt.date, rows: list[dict]) -> list[tuple]:
    """Advance ``state`` with one snapshot; return the output rows for ``asof_ts=observed_ts``.

    Output row layout matches ``schema.OUTPUT_COLUMNS``.
    """
    fp = fingerprint(rows)
    if fp != state.last_fingerprint:
        rows = dedupe(rows)
        assigned = match(rows, state.positions)
        touched: set[int] = set()
        for i, row in enumerate(rows):
            pos = assigned[i] if i in assigned else state.new_position()
            pos.absorb(row)
            touched.add(pos.position_id)
        # Duplicates that were issued earlier (company spelled two ways, a retitle that
        # arrived before we could tell) are folded as soon as a snapshot touches them.
        state.merges += consolidate(state.positions, touched)
        state.last_fingerprint = fp
    state.last_ts = observed_ts
    uid = state.user_id
    return [(observed_ts, uid, *p.values(), p.position_id) for p in state.positions]

def match(rows: list[dict], positions: list[Position]) -> dict[int, Position]:
    """Return ``{row_index: position}`` for rows that match an existing position."""
    cands: dict[int, list[Position]] = {}
    wanted_by: dict[int, list[int]] = {}
    for i, row in enumerate(rows):
        for pos in positions:
            if is_candidate(row, pos):
                cands.setdefault(i, []).append(pos)
                wanted_by.setdefault(pos.position_id, []).append(i)

    assigned: dict[int, Position] = {}
    taken: set[int] = set()
    # Rule 3: unique, uncontested candidate.
    for i, ps in cands.items():
        if len(ps) == 1 and wanted_by[ps[0].position_id] == [i]:
            assigned[i] = ps[0]
            taken.add(ps[0].position_id)
    # Rules 4 & 5: greedy by score for the contested rest; ties keep row order.
    scored = sorted(
        ((_score(rows[i], p), i, p) for i, ps in cands.items() if i not in assigned for p in ps),
        key=lambda t: (-t[0], t[1]),
    )
    for s, i, p in scored:
        if s < AMBIGUOUS_MIN_SCORE:
            break
        if i in assigned:
            continue
        if p.position_id in taken and s < DUPLICATE_SCORE:
            continue
        assigned[i] = p
        taken.add(p.position_id)
    return assigned

def coalesce_bucket(df: pl.DataFrame, states: dict[int, UserState] | None = None,

    ``history`` holds the cleaned rows of earlier runs. When it is given, a user whose new
    snapshots are not all newer than their state (late or re-delivered data) is replayed
    from scratch over history + new rows, and *all* of their as-of rows are emitted again
    (listed in ``restated``; their position ids may change). Without it such snapshots are
    quarantined as ``late_snapshot``. The returned ``history`` adds this run's rows.
    """

        states = {}
    df, clean_counts = clean(df)

        late = state.last_ts is not None and udf["observed_ts"].min() <= state.last_ts

        # earlier positions keep their ids and no half-updated rows are emitted.
        checkpoint, out_mark = copy.deepcopy(state), len(out)
        try:

                state = _replay(uid, pl.concat([history.filter(pl.col("user_id") == uid), udf]), out)

                    if state.last_ts is not None and ts <= state.last_ts:
                        skipped += 1
                        quarantine.append((uid, "late_snapshot", f"{ts} <= state {state.last_ts}"))

                    snapshots += 1
        except Exception as exc:  # isolate one user's failure from the rest
            quarantine.append((uid, type(exc).__name__, traceback.format_exc(limit=3)))

            if uid in states:
                states[uid] = checkpoint
            continue
        states[uid] = state

    positions, users = dump_state(states)
    return BucketResult(

        positions=positions,

        history=None if history is None else pl.concat([history, df]),
        restated=restated,
    )
