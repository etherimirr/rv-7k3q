照着说的顺序（每框一句）：

  • 1 来源：数据从哪来、每天多少、格式是什么、会不会迟到。
  • 2 接入：要秒级就 Kafka（按 user_id 分区保序），要天级就 S3 落文件每天跑一批。
  • 3 清洗：schema 契约、丢坏行不丢整批、修乱码、按内容哈希去重。
  • 4 核心：按 key 分区让同一个人的数据在一台机器上；逐 key 的有状态逻辑（这就是你的状态机）；一个 key 出错隔离不阻塞。
  • 5 存储：列式 parquet；表格式给事务、分区裁剪、时间旅行；状态按 key 分区只追加。
  • 6 服务：分析查询走仓库；点查走 KV + 缓存 + API。
  • 7 监控：每次运行出指标，突变告警，必须为 0 的硬断言。
  • 最后说三句：瓶颈在 4（算力线性加机器）和 5（小文件）；扩容靠分区数；取舍是 X 换 Y 因为 Z。

Any data pipeline is the same six boxes: sources, ingest, clean, core processing partitioned by key, storage, and serving, with monitoring across all of them and a state store feeding the next run. Let me draw that and then fill in each box for this problem.

1 · 估算（back-of-envelope）

比方：装修前先量房间，不用精确到毫米，知道是 50 平还是 500 平就够。

记住这几个数用法
1 天 ≈ 86,400 秒 ≈ 10 万秒每天 1 亿请求 ÷ 10 万秒 ≈ 1,000 QPS
1 KB × 10 亿 = 1 TB每行 1 KB、10 亿行 = 1 TB
一台机器：内存 64–256 GB，SSD 几 TB，网卡 1–10 Gbps超过就要分机器
内存读 100 ns、SSD 读 100 µs、跨机房网络 100 ms每差 1000 倍；能放内存就别读盘
一个 CPU 核每秒处理简单行：几万到几十万你实测 Polars 3.5 万行/核秒（含模糊匹配）

你的项目里：1000 亿行 × 约 500 字节 ≈ 50 TB 输入；3.5 万行/核秒 → 1000 亿 ÷ 3.5 万 ≈ 286 万核秒 ≈ 800 核时；64 核约 12 小时。输出约 1.08 倍输入。

At roughly 500 bytes a row, 100 billion rows is about 50 terabytes. At 35 thousand rows per core-second that's about 800 core-hours, so 12 hours on 64 cores or a bit over an hour on 640.

2 · 分区 / 分片 + 一致性哈希

比方：一个图书馆放不下，按书名首字母分到 26 个馆。分区就是「按什么键把数据切开放到不同机器」。

  • 按键取模（你的 user_id % 64）：简单、均匀。缺点：桶数一变，几乎所有数据都要搬家（100 % 64 = 36，100 % 65 = 35）。
  • 按范围（user_id 1–100 万一台）：范围查询方便，但容易热点（新用户都挤在最后一台）。
  • 一致性哈希：把哈希值想成一个钟面，机器和数据都落在钟面上，数据归顺时针最近的机器。加一台机器只搬它前面那一小段，约 1/N 的数据。虚拟节点：每台机器在钟面上放 100–200 个点，分得更均匀，机器性能不同还能放不同数量的点。
  • 热点键：某个 key 流量特别大（名人）。办法：key 后面加随机后缀拆开，或单独给它一台。
  • 二级索引：按 user_id 分区后，想按公司查就得问所有分区（scatter-gather），或者另建一份按公司分区的索引。

你的项目里：取模是对的，因为状态按桶存、同一个人必须回到同一桶，而且桶数你自己定、_meta.json 守着。被问「桶数要变怎么办」：用 history 全量重跑一次换桶数；生产上要平滑扩容就上一致性哈希或者表格式自带的分区。Spark 版 4096 分区；按 user_id 分区让 join 状态表时同一个人在同一台机器上，不用网络搬数据。

I partition by user_id mod 64 because state is stored per bucket and the same user must land in the same bucket next time. Modulo doesn't rebalance gracefully, so for elastic scaling I'd use consistent hashing with virtual nodes, or let the table format own the partitioning.

3 · 复制与一致性

比方：一份账本抄三份放三个地方，一处烧了别处还在。复制 = 同一份数据存多份。

  • 主从（leader–follower）：写只去主，从库跟着抄；读可以分给从库。抄有延迟 → 刚写完去从库读可能读不到（复制延迟）。
  • 强一致：写完所有人立刻看到同样的值。最终一致：一会儿之后大家才一样。数据流水线的输出通常接受最终一致（按天/按小时更新）。
  • CAP 一句话：网络断了（P 一定会发生）的时候，只能二选一：要么拒绝服务保证一致（C），要么继续服务但可能读到旧值（A）。
  • 多副本写冲突：两边同时改同一条 → 要定规则：最后写入赢（丢数据）、或者按版本号合并。

你的项目里：输出 parquet 放对象存储（S3 自带多副本），不用自己管复制；每天一版、最终一致。状态表用 Iceberg 的事务提交，读的人永远看到完整的一版，不会读到写一半。

For a daily batch output, eventual consistency is fine: readers see yesterday's complete version until today's commit lands atomically. I'd keep the data in object storage, which already replicates, and use a table format for atomic commits.

4 · 唯一 ID（Snowflake）

比方：车牌 = 省份 + 城市 + 序号，各段各管各的，不用全国排队领号。

  • Snowflake：64 位 = 1 位符号 + 41 位时间戳（毫秒）+ 10 位机器号 + 12 位每毫秒序号。每台机器自己发号，不用中心协调；按时间大致有序。
  • 为什么不用自增：要一个中心数据库发号，成了瓶颈和单点。为什么不用 UUID：128 位太长、无序、索引不友好。
  • 时钟回拨是 Snowflake 的经典坑：机器时间往回跳会发重号，要等时间追上来再发。

你的项目里：user_id << 16 | 每人序号。同样是「拆段、各管各的」，但不用时间戳，因为要可复现：同样输入每次必须发出同样的 id。user_id 最大 32 位 + 16 位序号 = 48 位，64 位放得下；每人上限 65,536，超了报错进隔离，不静默撞号；id 可以因规则 6 合并而退役，退役后永不复用。

Ids are user_id shifted left 16 bits plus a per-user sequence. It's the Snowflake idea, split the bits and let each part be issued independently, but without a timestamp, because the ids must be reproducible from the input.

5 · 缓存

比方：常用的调料放灶台边，不每次去储藏室拿。

  • cache-aside（最常用）：先查缓存，没有就查库，查到后写进缓存。写数据时删掉缓存里的旧值。
  • TTL：缓存多久过期。短 = 新鲜但命中低；长 = 命中高但可能旧。
  • 淘汰策略：满了删谁。LRU 删最久没用的；LFU 删用得最少的。
  • 三个坑：穿透（查不存在的 key，每次打到库 → 缓存空值）；雪崩（大量 key 同时过期 → TTL 加随机抖动）；击穿（一个热 key 过期瞬间大量请求 → 加锁只让一个去查）。
  • 命中率：命中次数 ÷ 总次数；80% 命中就把库的压力降到 1/5。

你的项目里：lru_cache 缓存 title_key / sim_key / desc_tokens 的结果（同一个头衔反复出现）；TikTok 那段的在线特征链路用过 20 分钟 TTL + 哈希降级，可以拿来当缓存设计的例子。

I'd put a read cache in front of the serving store with cache-aside and a TTL, add jitter to the TTL so keys don't all expire together, and cache negative results so missing keys don't hammer the database.

6 · 消息队列（Kafka）

比方：快递站的传送带。寄件人放上去就走，分拣员按自己的速度拿，带子上的包裹还能倒回去重看。

  • 三个用处：解耦（生产方和消费方不用同时在线）、削峰（高峰先排队）、可重放（消费方挂了从上次的位置接着读）。
  • Topic / 分区 / offset：一个 topic 切成多个分区；同一个分区内有序，跨分区无序；每个消费者记自己读到的位置（offset）。按 key（比如 user_id）分区，同一个人的消息就在同一分区、按顺序到。
  • 投递语义：至多一次（可能丢）、至少一次（可能重）、恰好一次（贵）。常用做法：至少一次 + 消费端幂等。
  • 消费者组：一组消费者分摊一个 topic 的分区，加消费者就加吞吐，但消费者数不能超过分区数。
  • 积压（lag）：生产比消费快，offset 落后越来越多，是最重要的监控指标。

你的项目里：每天的新观测可以从 Kafka 进来，按 user_id 分区，这样迟到数据和正常数据在同一个人的分区里；消费端用你的 step 函数，它本来就是幂等可重放的（同样的输入同样的输出）。

New observations would arrive on a Kafka topic partitioned by user_id, so one person's events stay ordered. Delivery is at-least-once and the consumer is idempotent, because step is deterministic, so a redelivered message can't produce a different result.

7 · 批处理 vs 流处理，迟到数据

比方：批处理是每天晚上结一次账；流处理是每笔交易当场记。

  • 批（Spark、MapReduce）：吞吐大、简单、延迟小时到天。流（Flink、Kafka Streams）：秒级延迟，但要处理乱序、迟到、状态管理，运维重。
  • 事件时间 vs 处理时间：事情发生的时间 vs 系统看到的时间。两者差 = 迟到。水位线（watermark）：系统宣布「X 时刻之前的事件应该都到了」，之后再来的算迟到，要单独处理（丢、或者回头更正）。
  • Lambda 架构：批 + 流两套，流给实时近似，批晚上修正。Kappa 架构：只用流，要重算就从队列头重放。
  • MapReduce 核心：map 按 key 打散 → shuffle 把同 key 聚到一台 → reduce 处理。贵的是 shuffle（网络搬数据）。
  • 数据倾斜：某个 key 的数据特别多，一台机器干到天亮别的都闲着。办法：热 key 加盐拆开、两阶段聚合、或者单独处理大 key。

你的项目里：选批，因为题目只要每天更新，流的复杂度用不上。observed_ts 是事件时间、到达日期是处理时间，迟到 = 两者不一致，你的处理是「只重放那一个人」，相当于迟到数据的回头更正。Spark 的 repartition by user_id 就是 shuffle；人均 29 条、最多 166 条，没有倾斜；真有超级用户就单独处理。

The brief needs daily freshness, so batch is the right tool; streaming would add ordering and state complexity for no gain. observed_ts is event time, arrival is processing time, and late data is handled by replaying just that person, which is the batch version of a watermark correction.

8 · 幂等、恰好一次、确定性重算

比方：电梯按钮按十次和按一次一样。幂等 = 同一个操作做多次，结果和做一次一样。

  • 为什么重要：分布式里重试不可避免（网络超时不知道成没成功），只有幂等才能放心重试。
  • 怎么做到：操作带唯一 id，做过就跳过（去重表）；或者操作本身是「设置成 X」而不是「加 1」。
  • 恰好一次通常 = 至少一次 + 幂等，或者事务性写入（输出和 offset 一起提交）。
  • 确定性：同样输入同样输出，没有随机、没有依赖时间或机器。有了确定性，重跑就是最简单的修复手段。

你的项目里：id 从 user_id 和首次出现顺序算出来，没有全局计数器 → 确定性；测试「跑两次结果一样」「全量 = 半量 + 增量」就是幂等和确定性的证明；输出文件先写临时再改名（原子写），跑一半挂了不会留半个文件；迟到数据直接重放，因为重放是安全的。

The pipeline is deterministic: same input, same ids, same output, with no global counter and no randomness. That's what makes retries and replays safe, and it's covered by tests: run twice equals once, and full equals half plus incremental.

9 · 存储：对象存储、列式文件、数据湖表格式

比方：S3 是无限大的仓库，parquet 是按列装箱的货物，Iceberg 是仓库的账本（哪些箱子算当前这一版）。

  • 对象存储（S3）：便宜、无限、自带多副本；但没有「追加」和「改一行」，只能整文件写。延迟高（几十毫秒），适合批不适合点查。
  • 列式（parquet）：同一列存在一起。好处：只读需要的列（你 conform 只读 10 列）；同列压缩率高；带统计信息（每块的最大最小值）能跳过整块（谓词下推）。坏处：改一行要重写文件。
  • 行式（数据库表）：一行存一起，点查快、改一行快。
  • 表格式（Iceberg / Delta / Hudi）：在一堆 parquet 文件上加一层元数据，提供：ACID 提交（一次写入要么全可见要么全不可见）、快照 / 时间旅行（回到任何一版）、MERGE（按键更新）、分区裁剪（按分区只读需要的文件）、schema 演进（加列不重写）、小文件合并。
  • 小文件问题：几百万个 1 MB 文件比几千个 1 GB 文件慢得多（打开文件有固定开销）。目标每个文件 128 MB–1 GB。

你的项目里：输出 parquet、每桶一个文件（64 个），大小合适；状态现在是 parquet 每天整份重写，生产应放 Iceberg 按 user_id 分区、MERGE 只更新动过的人、一次运行一次提交、旧版本留着回退；history 只追加。桶太多 = 小文件问题，所以桶数不是越多越好。

Output goes to parquet on object storage, one file per bucket. For state I'd use Iceberg partitioned by user_id: merge only touched users, one atomic commit per run, and snapshots so a bad run rolls back. Parquet's column pruning and min-max statistics are why reading only ten columns is cheap.

10 · 实体消歧 / 去重系统（record linkage）

比方：两本通讯录合并，「张伟 13800」和「Zhang Wei 138-00」是不是同一个人。

  • 三步：Blocking（先用便宜的键把候选缩小，比如同雇主）→ 成对比较（打分：相似度 + 规则或模型）→ 聚类 / 传递闭包（A=B、B=C → A=C，合成一簇）。
  • Blocking 为什么必须：N 条两两比是 N²；1000 亿行不可能。按 user_id 和雇主分块后，每人只有几十条。
  • 规则 vs 模型：规则可解释、可复现、快；模型（逻辑回归 / 梯度提升 / embedding）召回高但要标注、要可复现地部署。常见做法：规则做主、模型只用在规则拿不准的那层。
  • 评估：成对指标（配对的精确率 / 召回）vs 簇指标（B-cubed）；没有标准答案时抽样 + 判官 + 人工 + 无标注健康度。
  • 传递性的坑：A 像 B、B 像 C，但 A 和 C 一点不像，链式合并会把不相关的合成一团。要么限制簇大小，要么要求和簇里多数相似。

你的项目里：规则 2 就是 blocking（同雇主 + 日期兼容才算候选）；规则 4–5 是成对比较；规则 6 是把已发出的 id 做传递合并，但只在被动过的职位上做、且要同开始日期，避免链式乱合。学习打分器试过、没上线，下一步只用在弱点层。

It's a standard record-linkage shape: blocking by employer and date to keep candidates small, pairwise scoring with rules, then a constrained merge of duplicate ids. Rules first because they're reproducible and explainable; a learned scorer only where the rules are unsure.

11 · 数据质量监控与可观测性

比方：工厂流水线上的质检员，不等客户投诉才发现次品。

  • 三类指标：量（行数、人数、文件数，和昨天比差多少）、质（空值率、重复率、日期倒序数、覆盖率）、时效（数据几点到、跑了多久）。
  • 告警规则：和历史同期比，偏离 3 个标准差或者某个百分比就报警；绝不能为 0 的指标（主键重复、倒序日期）直接硬断言。
  • 数据契约（data contract）：上游保证 schema 和含义不变，变了要通知；你的 conform 「缺列直接报错」就是契约的硬执行。
  • 金丝雀 / 回归测试：固定一小份输入，每次跑完对比输出是否变化。
  • 隔离而不是整体失败：坏的一小部分进隔离区，其余照常出，事后看隔离区。
  • 血缘（lineage）：这列数据从哪来、经过哪些步骤，出了问题能追。

你的项目里：run.json 里的指标（输入行、输出行、丢弃行按规则、修复格数、合并数、重放人数、隔离人数）就是质量看板；覆盖率 99.94%、倒序日期 0、可疑拆分 3.7 万是无标注健康度；quarantine 目录是隔离区；51 个测试里的金丝雀。被问「上线后怎么知道结果还好」：每天看这几个数的走势，突变就查。

Every run emits metrics: rows in and out, drops per rule, repairs, merges, replays, quarantined users. I'd chart those daily and alert on deviations, hard-fail on anything that must be zero like duplicate keys or inverted dates, and keep the quarantine folder so one bad user never blocks the run.

12 · 服务层：把结果给下游用

比方：仓库里的货要上货架，顾客才拿得到。批处理的结果要有人能查。

  • 两种读法：分析查询（整表扫描、聚合）→ 直接读 parquet / 数据仓库（BigQuery、Snowflake、Trino）；点查（给我这个人的履历）→ 要 KV 存储（DynamoDB、Cassandra、Redis），按 user_id 做键，毫秒级。
  • 批到线上的搬运：每天跑完把结果批量写进 KV（bulk load），或者只写动过的人。
  • API 设计：GET /users/{id}/positions?asof=2026-10-01；分页；版本号；限流。
  • Cassandra / DynamoDB 一句话：按分区键哈希分片、多副本、最终一致、写快读快，不擅长复杂查询和 join。
  • 读写分离：批处理写一份，线上读另一份，互不影响。

你的项目里：下游要查「某人截至某天的履历」→ 按 (user_id, asof_ts) 做键放 KV；每天只有动过的人要更新，正好和增量输出对上；restated 名单告诉下游哪些人的历史行要整体替换。

For point lookups I'd load the daily output into a key-value store keyed by user and as-of date, updating only the users touched that day, and the restated list tells the loader which users need their history replaced.

押题最终答案（三道，每道一张图 + 最优设计）

题 A · 每天几亿条档案进来，维护去重后的「每人职业经历」（= 你的 take-home 上生产）

先问：每天多少条（设 3 亿）、新鲜度（天级够）、下游谁读（分析 + 点查）、要不要保留历史版本（要，as-of）。

估算：3 亿行/天 × 500 B = 150 GB/天；存量 1000 亿行 ≈ 50 TB；每天只有约 1% 的人有新数据；按 3.5 万行/核秒，每天增量 3 亿行 ≈ 2.4 核时，几台机器半小时。

  • 核心：和作业一样的 coalesce_bucket，Spark mapInArrow 调同一个函数；按 user_id 分区所以状态 join 不用跨机器。
  • 状态：Iceberg 按 user_id 分区、只 MERGE 动过的人、一次运行一次提交、旧快照留着回退；history 只追加、只给迟到的人读。
  • 迟到：事件时间 observed_ts；比状态旧的只重放那一个人，restated 告诉 KV 加载器整体替换。
  • 隔离：一个人出错回滚进隔离区，不阻塞当天运行。
  • 服务：分析走仓库；点查走 KV（key = user_id，value = 当前履历 + as-of 索引）+ 读缓存。
  • 扩容：人独立 → 加 executor 线性；分区数调到每分区几十万行；超级用户单独处理。
  • 取舍：天级批而不是流（新鲜度要求天级，流的乱序和状态管理不值）；规则而不是 LLM 逐对（可复现、可解释、1000 亿行成本）；merge when in doubt。
  • 隐私：删除名单在输出时过滤。

Same core as the take-home, run under Spark partitioned by user_id, with state in an Iceberg table partitioned by user_id so each day merges only touched users and commits atomically. Late data replays one person; failures are quarantined. Output goes to a warehouse for analysis and a key-value store for point lookups, and every run emits the quality metrics I alert on.

题 B · 职位名 / 技能映射服务（1000 万种原始职位名 → 标准分类）

先问：分类表多大（几千类）、延迟要求（线上毫秒 vs 离线批）、准确率目标、要不要多语言、分类表会不会改版。

估算：去重后约 1000 万种头衔，但头部几千种覆盖 80% 流量；线上 QPS 设 1 万；每个向量 384 维 × 4 B ≈ 1.5 KB，1000 万 × 1.5 KB = 15 GB，一台机器放得下。

  • 三层漏斗：规则/缓存吃掉大头（毫秒、确定）；embedding 吃长尾（几毫秒）；LLM 只处理低置信（贵、慢、结果缓存后不再调）。
  • 为什么不全用 LLM：1000 万次调用成本，答案不稳定，线上延迟；LLM 的价值是兜底 + 当判官。
  • 版本化：分类表改版要能回算历史，不然时间序列断；映射表记来源（规则 / 向量 / LLM / 人工）。
  • 评估：按频次分层抽样（头部错一个影响大）；LLM 判官用人工样本校准；监控「进 LLM 的比例」「进人工的比例」，涨了说明有新词。
  • 多语言：多语言 embedding 模型；词表先翻译。
  • 取舍：准确 vs 延迟 vs 成本，用置信度阈值调；阈值高 → 更多进 LLM/人工。

A three-tier funnel: normalise, then rules and a cache for the head of the distribution, embedding nearest-neighbour for the long tail, and an LLM only for low-confidence cases, with results cached and the lowest sent to human review. The mapping table is versioned so history can be recomputed, and I evaluate on frequency-stratified samples with an LLM judge calibrated against human labels.

题 C · 公司实体消歧 + 数据质量监控

先问：公司实体来源（档案里的公司名、URL、官网、注册信息）、要合并到什么粒度（法人 vs 品牌 vs 子公司）、改名/并购怎么算、下游要什么（公司级统计）。

估算：几亿条公司提及，去重后几千万个名字，真实公司几百万；两两比不可能 → 必须 blocking。

  • 三步：blocking（域名最强、名字前缀 / 首字母 / 音似兜底）→ 成对打分（名字 + 域名 + 地址 + 行业）→ 受限聚类（限制簇大小，防 A 像 B、B 像 C 的链式乱合）。
  • 别名集合 + 改名历史：一个公司记所有叫过的名字和域名；并购是关系不是合并（Jeppesen/Boeing 那种）。
  • 种子数据：官方注册库、上市公司、域名库当锚点，先把大公司钉死。

Standard record linkage: normalise names and domains, block on domain and name prefix, score pairs on name similarity plus domain, address and industry, then cluster with a cap on cluster size to avoid chaining. Each company keeps an alias set and rename history; mergers are relationships, not merges. Official registries seed the big companies. For quality I track new-id and merge rates, max cluster size and coverage daily, sample with judges, and route oversized or low-confidence clusters to human review. Here a wrong merge hurts more than a missed one, so unlike the take-home I split when in doubt.

13 · 其他常被问的一页

  • 负载均衡：把请求分给多台机器（轮询 / 最少连接 / 按哈希）；本身要双活防单点。
  • 限流：令牌桶（匀速放令牌，有令牌才能过，允许短突发）；滑动窗口计数。
  • CDN：静态内容放到离用户近的节点。
  • 数据库索引：B 树，像书的目录；加速读、拖慢写；查什么就按什么建。
  • SQL vs NoSQL：要事务和复杂查询用 SQL；要水平扩展、简单键值、灵活 schema 用 NoSQL。
  • 分布式锁 / 单写者：同一时刻只允许一个人改，租约 + 过期防止持锁者挂掉。
  • 隐私：被遗忘权 → 删除名单在输出时过滤；日志不打描述原文。
  • 容错：重试 + 退避 + 幂等；超时；断路器（下游挂了就先别打）；单桶重试而不是整体重跑。

15 · 英文口述版 · 一句话库

  • Partitioning: "I'd partition by user_id so all of one person's data lands on one worker; nothing is shared across people, so it scales linearly."
  • Consistency: "It's a daily batch, so eventual consistency is fine as long as each day's output is published atomically."
  • Queue: "A Kafka topic partitioned by user_id keeps one person's events in order; the consumer is idempotent so at-least-once delivery is safe."
  • Batch vs stream: "The freshness requirement is daily, so batch wins; streaming would add ordering and state complexity with no benefit."
  • Late data: "observed_ts is event time; when something arrives late I replay only that user, which is cheap and verifiable."
  • Storage: "Parquet on object storage for the output; Iceberg for the state so I can merge only touched users and roll back a bad run."
  • Monitoring: "Each run emits counts per rule; I'd alert on deviations and hard-fail on anything that must be zero."
  • Trade-off line: "I chose X over Y because of Z; the cost is W, and here's how I'd notice if W becomes a problem."
